# Life Planner Back — Claude Context Router

NestJS 10 / TypeScript (strict) REST API for the Life Planner app (families: finances, stock/home storage, family members).
Postgres via Prisma 7 (`@prisma/adapter-pg`), Zod 4 + `nestjs-zod` validation, JWT auth (bcrypt), Pino logging, Swagger at `/swagger`.
Clean Architecture / DDD: `src/api` (controllers + services) → `src/modules/<module>/application` → `src/modules/<module>/domain` ← `src/modules/<module>/data` (← `src/shared/infra`).

**Frontend repo:** `../life-planner` (Expo / React Native, sibling folder; remote `git@github.com:salomaoluiz/life-planner.git`, https://github.com/salomaoluiz/life-planner — if the folder is missing, ask the user before cloning it next to this repo, or read it on GitHub). Read `.claude/context/integration.md` whenever a change affects the API contract, auth, ids/enums or the data model — the frontend consumes this API. Its own router is `../life-planner/.claude/CLAUDE.md`.

## Golden rules (non-negotiable)

1. **Domain is pure TS** — entities, repository interfaces and domain errors import nothing from Nest/Prisma/npm (the existing `NotFoundException`s thrown in use cases are the accepted exception, in application only).
2. **Dependency direction** — api → application → domain; data implements domain interfaces. **`src/api` is the single entrance (BFF-style)**: it only validates, calls the use cases exported by the modules and **aggregates** their results into the response — one endpoint may combine several modules (finance + stock + family) when needed, or be a plain CRUD. It holds **no business rules**: those live inside the modules (use cases/entities, extending `UseCase` / `UseCaseWithParams`), so modules never depend on each other and `api` never touches repositories/datasources. Modules export use cases only.
3. **Persistence isolation** — Prisma types (`@db/client`) appear only in `data/` (datasource, mapper). Entities are plain classes, never Prisma models; convert through a mapper.
4. **Infra libs through `@shared/infra`** — outside `src/shared/infra` don't import external libs directly (allowed: `zod`, `nestjs-zod`, `@nestjs/*`, `jest`, `@faker-js/*`). Enforced by ESLint.
5. **DI by interface token** — `@Inject('IUserRepository')`, `@Inject('IUserDatasource')`, etc.; bind with `{ provide, useClass }` in the module.
6. **Validate every input at the boundary with Zod** (`validate()` or `createZodDto` schemas). Never return `password_hash`/`passwordHash`. Protected by default (global `JwtAuthGuard`); opt out only with `@Public()`.
7. **Authorization, not just authentication** — a valid JWT is not enough: check the resource belongs to `req.user.id` (or the user's family). Known gap: `GET/PATCH /v1/user/:id` currently lets any authenticated user read/update any user; don't copy that pattern into new endpoints.
8. **Path aliases only** (`@shared/*`, `@api/*`, `@user/*`, `@finance/*`, `@family/*`, `@investment/*`, `@stock/*`, `@db/*`); never `../../`. No `any`, `@ts-ignore` or lint-disable to bypass rules.
9. **Tests are mandatory** — every use case, entity, datasource, repository, controller, service and infra wrapper gets `index.test.ts` + `index.mocks.ts` (90% global coverage threshold). Test files and fixtures use fake data only.
10. **API contract changes affect the frontend** — a changed route, payload, status code, enum or id format must be reflected in `../life-planner` (see `integration.md`). Call it out to the user; don't edit the frontend repo unless asked.
11. **Keep context in sync** — after changing a pattern, update the matching `.claude/context` file and the "Current state" section above; flag new flows/patterns so `.github/copilot-instructions.md` can be updated too.
12. **Commits & hooks** — conventional commits. Husky `pre-commit` runs `lint-staged` (lint + prettier), `type-check` and tests on staged files; `pre-push` runs `yarn lint` and `yarn test --coverage`. Fix what the hooks report; don't bypass them (`--no-verify`).
13. **Never commit secrets or personal data.** Covers `.env` contents (DB credentials, `JWT_SECRET`), tokens, keys, connection strings and real personal info (names, emails, real user/family ids, financial data).
    - Config goes in `.env` (gitignored) read through `EnvService` / `envSchema`; never hard-code values in source, tests, Docker files or docs. New variables must be added to `envSchema`, `docker-compose.yml` and, as a placeholder-only entry, to an `.env.example` (create it if missing).
    - Tests and mocks use fake data (`faker`, `test@example.com`, random UUIDs).
    - **This is an open source project.** Nothing that identifies the owner or their infrastructure may be committed, in code, tests, docs, scripts, commit messages or PR descriptions: real domains/hostnames, IP addresses, server or host names, local paths and usernames, personal or company emails and names, account and project identifiers. Use placeholders (`example.com`, `your-...`, `<HOST_IP>`, `/Users/<you>/`). Re-read the staged diff and the commit message for these before every commit and PR. If one was already pushed, stop and tell the user (history rewriting needs their approval).
    - Before every commit review `git diff --cached`; stage files explicitly (no `git add -A` / `git add .`). If anything looks secret or personal, unstage it, don't commit, and tell the user. If a secret was already committed, stop and tell the user (it must be rotated); don't rewrite history yourself.
14. **E2E guardrail (Maestro, flows live in `../life-planner/e2e`).**
    - Runs follow three stages (same as frontend rule 12), each starting only when the previous one is green; use `zsh -ic 'yarn e2e --headless …'`. (1) The spec's own flows while building (`yarn e2e --tags spec-NNN`; none for a backend-only slice). (2) Related flows: `yarn e2e --changed` (reads the changed files of both repos, selects the matching module flows plus `smoke`; shared paths such as `prisma/` or `src/shared/` select everything). (3) Once, before reporting any change to `src/` or `prisma/` as done and before the PR, the rest of the suite: `yarn e2e --unchanged` after a green `--changed` (it runs only the flows `--changed` did not select, so nothing runs twice), or the full `yarn e2e` when `--changed` was not run. It runs the app's Maestro flows against the API the owner keeps running in watch mode on the Mac, so it tests this working tree. If the change includes a Prisma migration, apply it locally with the repo's migration command first. Read **only** the summary it prints (`../life-planner/e2e-report/summary.md`), the same way as frontend rule 12.
    - A failing flow after a backend change is a regression of this change until proven otherwise. Fix the backend; do not edit flows, screens or anything else in `../life-planner` to make it pass unless the owner asked for the frontend change too (rule 10).
    - If the failure is caused by an intended API contract change (rule 10), stop and tell the owner which flows broke and which frontend change they need. That is the expected way the guardrail flags cross-repo work.
    - A backend-only feature with no screen yet needs no new flow. Its flow arrives with the frontend slice that uses it. The backend still runs `--changed` and then the full suite to prove nothing that exists broke.
    - E2E runs only on the owner's Mac (same as frontend rule 12). Exit code 2 (could not run: cloud session, API or app not running, sibling folder missing): say so in the final report; never claim the change was validated.
15. **Destructive-action guardrail.** If a task, spec or plan would require a destructive action outside the scope of the spec being implemented, stop and ask the owner before doing it, and wait for the answer. This covers deleting data of a real (non-test) user, force-pushing, rewriting history, resetting or discarding someone's uncommitted or unpushed work (including unpushed local commits and branches you did not create), and deleting branches, files or databases the task did not create. It applies to every feature and plan, in both repos, and a plan or an owner's earlier approval for one action does not extend to another.
16. **Version and changelog guardrail.** Every PR that touches shipped paths (`src/`, `prisma/`, `Dockerfile`, `docker-compose*.yml`, `package.json` dependencies, `yarn.lock`) bumps `package.json` `version` once (breaking → major, `feat` → minor, anything else → patch, from the latest `origin/main`) and adds a matching `## [x.y.z] - YYYY-MM-DD` entry at the top of `CHANGELOG.md` with 1–5 short user-facing bullets (English, spec number when there is one). Docs/tests/CI-only PRs don't bump. Re-bump after a rebase if `main` moved. `yarn version:check` must pass before the PR (Husky `pre-push` and the `version-check` CI job run it). Merging tags `vX.Y.Z` through the `release` workflow.
17. **Performance guardrail.** Details, commands and registry format: `.claude/context/performance.md`.
    - Every PR that changes `src/` or `prisma/` runs `yarn perf --changed` and is opened only when it ends `PERF PASSED` (read only `perf-report/summary.md`). Shared paths select every module.
    - The PR description has a "Performance" block: modules checked, the summary line, and before/after for any budget that changed.
    - Always run the perf check (`yarn perf --changed`) before opening the PR, every time, even for a change that looks unrelated to performance. Never run it with `--update-baseline` by default: update a baseline only when you are absolutely sure your change is what lowered it (same PR, reviewed diff, and say so in the PR); a baseline never moves because the local data or machine differs, or to turn a failing run green.
    - Never run the perf check (`yarn perf`, `yarn perf:check`) from a git worktree: its numbers are not comparable with the baselines (measured on this Mac: the same main code took ~850 ms in a worktree and ~450 ms in the repo checkout). Bring the branch to the repo checkout itself (switch it to the branch, after confirming the working tree is clean or asking the owner) and run the check there; baselines are only ever compared or updated from numbers taken in the repo checkout. Building and unit tests may still run in a worktree.
    - Budgets only go down silently; raising one needs a reason in the PR and the owner's review.
    - Every new route gets its registry entry (`perf/budgets/<module>.json`) in the same PR; the coverage tests fail otherwise.
    - Lists of any module have a period or pagination; a list over 256 KB needs a `knownException` with the spec that removes it.
    - Money data is never cached with `max-age`; caches are `private, no-cache` plus validation.
    - Backend: a new `include` in a list read must be justified by the query budget.
    - If `yarn perf` cannot run (exit 2: database, seed or build), say so in the final report with its one-line reason; never claim the change was checked.

18. **PR verification status guardrail.** Only the owner and the AI change this repo, so a failure that was not there before entered through a PR, and it is the AI's job to prove or disprove that it was this one.
    - Every PR description has a "Verification" section, written when the PR is opened and **rewritten every time the PR is updated** (new commits, rebase, fix): the unit tests (`yarn test`: total and result), the performance check (`yarn perf --changed`: modules and the `PERF PASSED: N/N` line), the E2E (the summary line of the last run, and every failed flow by name) and `yarn version:check`. Never report a check that was not run in this PR's last state; say "not run" and why.
    - When a check fails and it looks unrelated to the change, do not conclude "pre-existing" from one run on `main`. Open the **last merged PR** of the repo (`gh pr list --state merged --limit 1`) and read its Verification section. If it was green there, the problem came in with the current changes or it is an intermittency: investigate and fix it (rerun alone, `e2e:failed`, look at the screenshot and the log) before opening or updating the PR. Only if the last merged PR also reported that same failure may it be left, and then the PR names the flow or test, the PR where it started and why it was not fixed.
    - A failure left open is always listed in the PR description with that evidence; a green summary must never hide a failed flow.

19. **Stay on the branch when the work ends.** Start new work with `git fetch origin main && git checkout -b <branch> origin/main` (never from a stale local `main` or another feature branch) and, when the work is finished (PR opened, checks run, final report), leave the checkout on that branch. Never `git checkout main` afterwards "to clean up"; the next task cuts its own branch from `origin/main`. Switch to another branch only when a check requires it and switch back right after. Same rule as the frontend's rule 11.
